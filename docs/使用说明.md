# multi-credits-pool 使用说明

管理多个 WorkBuddy 账号的登录凭据，每天自动签到，把各账号的积分与套餐汇总到一张表；并把这些账号的模型额度轮换起来，作为 DSH 模型选择器里的一个 provider。

## 运行环境

- Windows（计划任务部分依赖 `schtasks`）。
- Node.js 22.19 及以上；或直接用 DeepSeek Harness 桌面版自带的运行时，无需另装 node。
- 能够访问 `www.workbuddy.cn`（国内账号）或 `www.workbuddy.ai`（国际账号）。

## 安装与准备

工具不需要安装，克隆或解压后直接运行 `bin/credits.js`。两种启动方式等价：

```powershell
# 1) 机器上已有 node 22.19+
$env:DSH_PROFILE = 'desktop'
node bin/credits.js help

# 2) 用 DSH 桌面版自带的运行时（把路径换成自己机器上的安装位置）
$env:DSH_PROFILE = 'desktop'
$env:ELECTRON_RUN_AS_NODE = '1'
& 'D:\DeepSeek Harness\DeepSeek Harness.exe' --expose-internals '<插件目录>\bin\credits.js' help
```

下文用 `credits` 代指上面对应的一条命令前缀。想直接敲 `credits`，可在 PowerShell 里加一个函数：

```powershell
function credits {
  $env:ELECTRON_RUN_AS_NODE = '1'
  & 'D:\DeepSeek Harness\DeepSeek Harness.exe' --expose-internals '<插件目录>\bin\credits.js' @args
}
```

`<插件目录>` 是本仓库克隆到本机后的路径，例如 `D:\tools\multi-credits-pool`。

两个环境变量的作用：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DSH_HOME` | `~/.dsh` | 数据根目录 |
| `DSH_PROFILE` | `default` | profile 名；桌面版实际使用 `desktop` |

数据落在 `$DSH_HOME/profiles/$DSH_PROFILE/.multi-credits-pool/`。`credits where` 打印这个路径。

## 账号

一个账号一条记录，可以放任意多个。`login` 每次追加一个，重复登录同一账号是覆盖。

```powershell
credits login --label 主号                # 国内站，浏览器里完成授权
credits login --global --label 国际号      # 国际站
credits login --label 小号 --no-open       # 不自动打开浏览器，只打印授权链接
credits login --label 备用 --timeout 600   # 放宽等待授权的时长（秒，默认 300）
```

`login` 会打印一个授权地址并在默认浏览器中打开。在浏览器里用要添加的账号登录并确认，终端侧每 2 秒查询一次进度，完成后自动保存凭据并显示账号 uid。

已经有一份凭据 JSON 时可以直接导入，不必再走浏览器：

```powershell
credits import .\acct.json --label 备用
credits import .\acct.json --global    # 国际站凭据要显式声明
```

凭据文件只需要一个字符串字段 `accessToken`；其余字段（`refreshToken`、`uid`、`nickname`、`domain`、`expiresAtMs`）有就一并写入。文件带 UTF-8 BOM 也能正确解析。

查看与管理：

```powershell
credits list                 # 表格：ID、账号、区域、令牌、最近签到
credits list --json          # 机器可读；不含令牌内容，只报有没有
credits rename 主号 家里号     # 改显示名（也接受账号 id）
credits remove 家里号         # 删账号
```

`令牌` 一列显示访问令牌的剩余天数，已过期显示 `已过期`，没有到期信息时显示 `(导入)`。过期但有 refreshToken 的账号会在下次签到或查询时自动续期；没有 refreshToken 且已过期的账号只能重新登录或导入。

## 每日签到

### 手动签到

```powershell
credits checkin                 # 所有账号签一遍，今天签过的跳过
credits checkin --id 主号        # 只签一个账号
credits checkin --force         # 今天签过也重签
credits checkin --quiet         # 只输出错误，便于脚本调用
credits pending                 # 只列出今天还没签的账号 id，没有任何输出表示都签完了
```

签到按账号顺序逐个执行，账号之间间隔 1.2 秒。单个账号失败不会中断后面的账号，失败的账号会在结尾以 `✘` 标出并计入退出码。

输出里的四种结果：

| 标记 | 含义 |
| --- | --- |
| `✔` | 签到成功，后面是领到的积分数 |
| `•` | 今天已经签过（上游判定），不重复领 |
| `-` | 签到活动未开启或已结束 |
| `✘` | 失败，后面是原因 |

### 常驻进程

```powershell
credits daemon                  # 默认每天 10:00（UTC+8）签一次
credits daemon --at 08:30       # 指定时刻
credits daemon --quiet
```

启动时如果当天已经过了签到时刻，会先补签一次；之后每天到点执行。进程退出即停止签到，适合 DSH 长时间开着的场景。

### Windows 计划任务

DSH 没有启动、插件没有加载时，仍然需要每天签到，就把签到注册成系统任务：

```powershell
credits schedule-install --at 10:00 --dry-run   # 先看会生成什么文件、执行哪条命令
credits schedule-install --at 10:00             # 真正注册
credits schedule-status                         # 是否已注册、下次运行时间
credits schedule-remove                         # 删除任务与生成的脚本
```

注册的任务名是 `DSH Multi Credits Pool Checkin`，每天在 `--at` 指定的时刻执行一次，时刻按**本机时区**解释；动作是数据目录下的 `run-checkin.cmd`，它会转调同目录的 `checkin-task.ps1` 并执行 `checkin --quiet`，输出追加到 `checkin-cron.log`。

`--dry-run` 不写文件、不调 `schtasks`，只打印两个脚本的内容与完整命令行，适合在受策略限制的机器上先确认。

重复执行 `schedule-install` 会覆盖同名任务，可以随时用新的时刻重新注册。

## 查看结果

```powershell
credits status                 # 一屏表格：今日签到、剩余积分、套餐数、令牌有效期
credits status --no-balance    # 不请求余额，只看签到（快，不发网络请求）
credits status --json
credits report --out 汇总.md    # Markdown 报告：今日、账号明细、套餐明细、本月累计
credits report --json
```

余额是逐账号的实时请求。某个账号读取失败时，只有那一行显示「读取失败（原因）」，其余账号照常输出；签到状态来自本地流水，不受余额接口影响。

`report` 的本月累计统计的是流水里本月所有 `claimed` 记录的积分数之和。

## 在 DSH 里使用（模型轮换）

装进 profile 后，DSH 的模型选择器里会多出一个 provider「multi-credits-pool」。选它下面的模型时，请求由插件按账号顺序轮换发出，界面上和用内置 provider 没有区别。

### 安装

先把仓库克隆到本机（`<插件目录>` 指克隆下来的目录），然后在仓库根目录运行：

```powershell
$env:DSH_HOME = "$env:USERPROFILE\.dsh"
$env:DSH_PROFILE = 'desktop'
$env:ELECTRON_RUN_AS_NODE = '1'
& 'D:\DeepSeek Harness\DeepSeek Harness.exe' --expose-internals '<插件目录>\tools\install-plugin.mjs'
```

机器上已有 Node.js 22.19+ 时，`& '...\DeepSeek Harness.exe' --expose-internals` 可以换成 `node`，例如 `node tools\install-plugin.mjs`。

脚本做两件事：把包复制到 `%DSH_HOME%\profiles\desktop\node_modules\multi-credits-pool`，把包名追加到该 profile `package.json` 的依赖与 `dsh.profile.bundles`。改清单前会先备份成 `package.json.bak-<时间戳>`。

装完要完全退出 DSH（包括托盘图标）再启动。卸载用同一个脚本加 `--remove`。

默认是复制安装：装完再改代码不会同步，要重装才生效。开发态可以改用目录联接，让装进去的那份直接指向工作区：

```powershell
& 'D:\DeepSeek Harness\DeepSeek Harness.exe' --expose-internals '<插件目录>\tools\install-plugin.mjs' --link
```

做联接前必须先退出 DSH：宿主进程持着已加载的文件句柄，装着的时候删旧目录会失败。

### 装完没出现怎么办

数据目录里的 `boot.log` 记录插件启动走到哪一步：

```powershell
Get-Content "$env:USERPROFILE\.dsh\profiles\desktop\.multi-credits-pool\boot.log"
```

| 最后一行 | 含义 | 处理 |
| --- | --- | --- |
| 文件不存在 | 包没被宿主导入 | 确认 profile `package.json` 的 `dsh.profile.bundles` 里有 `multi-credits-pool`，且 `node_modules` 下有这个包 |
| 只有 `module-loaded` | 导入了但 `apply` 没被调用 | 插件挂在 pending，检查 `inject` 要求的服务是否存在 |
| `apply-failed … cannot get property "settings" without inject` | 没把 `settings` 声明成注入依赖 | 换回声明了 `inject = ['settings']` 的版本 |
| `provider-registered …` | 登记成功 | 模型选择器里应有「multi-credits-pool」；没有就重启 DSH |

数据目录跟着 profile 走：桌面 App 不往环境变量里放 profile 名，插件靠「哪个 profile 声明了本包」反查，所以 `boot.log`、`plugin.json`、`accounts.json` 都在实际加载插件的那个 profile 下。CLI 场景按 `DSH_PROFILE` 走；两者不一致时以声明了本包的 profile 为准，`DSH_MULTI_CREDITS_POOL_DATA_DIR` 可以整体覆盖。

### 第一次使用

1. `credits list` 确认账号库里已经有账号；
2. 打开模型选择器，展开「multi-credits-pool」，选一个模型；
3. 发一条消息。令牌快到期时第一次请求会先续期，随后正常出字。

### 模型清单与可见性

模型清单不用手写：插件启动 15 秒后从上游取一次，之后每 24 小时取一次，结果缓存在 `plugin.json` 的 `models` 里。上游新上线的模型下一次刷新就会出现在选择器里，下线的从清单里消失。

「自动化」页签底部的「模型选择」卡片列出当前清单，勾上的才会出现在 DSH 的模型选择器里。不想在切换模型时被一堆用不到的模型占位，就取消勾选；改动立刻生效，不用重启。取消勾选记录的是「哪些不显示」，所以之后新上线的模型默认可见。至少要留一个，全都不勾会被直接拒绝。

清单取不到时（没有登录账号、网络不通）保持上一次的缓存不动，卡片头部仍显示上次更新时刻；点「立即更新」可以手动重试。

### 推理等级

模型支持推理时，DSH 的模型选择器里会多出一个推理等级下拉，可选档位由上游清单声明：`low` / `medium` / `high` / `xhigh` / `max`，选中后这一段对话就按那一档思考。

档位是上游自己列的，不是插件猜的：上游列了哪些档，下拉里就只有哪些。只声明了默认档的模型（比如 `auto`、`glm-5.2`）下拉里就一项。升级插件时插件会按已知的档位先补一次，不必等到下一次清单刷新。

档位越高思考越长、输出上限里留给思考的份额越多。`max` 档在短输出上限下可能把额度全用在思考上，回答变短甚至为空；遇到这种情况把 `max_tokens` 调大或换低一档。

### 升级插件

看板顶栏右上角的「检查更新」点一下，就会去 npm 上问一次有没有新版本（结果缓存 10 分钟）。

查到新版本时，这个按钮会直接变成「可升级 vX.Y.Z」并转成琥珀色，标签栏下面横一条提示，写着当前版本、最新版本和该执行的命令。面板不负责装——运行中的文件被 DSH 拿着，换不掉——复制那条命令到终端执行：

```powershell
multi-credits-pool update
```

装完完全退出 DSH 再启动，新版生效。

`update` 的几个用法：

| 命令 | 作用 |
| --- | --- |
| `multi-credits-pool update` | 装最新版 |
| `multi-credits-pool update --check` | 只查版本，不安装 |
| `multi-credits-pool update --to 0.3.8` | 装指定版本，可用来回退 |
| `multi-credits-pool update --registry https://registry.npmmirror.com` | 换镜像源 |
| `multi-credits-pool update --pnpm "D:\…\pnpm\bin\pnpm.cjs"` | 指定用哪个 pnpm |
| `multi-credits-pool update --dry-run` | 只打印将要执行的命令，不真装 |

装包用的是 pnpm，但桌面应用自带的 pnpm 藏在安装目录里、不在 `PATH` 上，普通命令行里直接敲 `pnpm` 会失败。命令会依次去找：环境变量 `MULTI_CREDITS_PNPM` → `PATH` 上的 pnpm → 宿主上次启动时记下的自带 pnpm（`.multi-credits-pool\runtime.json`）→ 在常见安装目录里扫一遍。都找不到时自动退回 `npm install`，并在输出里写明用的是哪个。想固定用某一个就加 `--pnpm`。

装完后命令会再读一次实际版本，报出来的是装完的真实结果，不是「应该装成了」。

### 指定某段对话的账号

对话标题栏右侧有一个账号按钮，显示这段对话当前会走哪个账号（`跟随：某某`）。点开是账号列表，选一个即固定下来，按钮变成绿点加账号名；菜单底部「解除固定」回到自动分配。

- 固定只对「对话固定」这一种调用方式生效。当前是别的模式时，菜单里的账号项是灰的，菜单顶部会说明要先切回「对话固定」。
- 固定的账号被删掉、或者进了冷却，这段对话会按当前排序走别的账号，固定记录留着，冷却结束后再回去。
- 按钮上的账号名是「下一个请求会用的账号」，不是「上一个请求用过的账号」。两者通常相同，切换模式或账号冷却时会有出入。

### 使用看板

看板回答「额度被谁烧在哪了」：按账号分组，每个账号下面按模型拆开，段的宽度是该模型在这个账号上的请求数占比，颜色只用来区分模型、不表示好坏。上面四个指标是近 7 天的请求总数、失败数、输入 token、输出 token。最下面是按天的请求数柱状图，只有超过一天的数据才画。

统计窗口固定 7 天，流水超过 2 万行时自动压缩成最近的部分。token 两格取自上游响应末尾那片用量读数：流式响应里它出现在最后一个 chunk，代理一边透传一边顺手记下；上游整段不给用量时这两格是 0，请求数不受影响。

看板只统计经过本插件的请求。对话选的是别的 provider（模型选择器里别家分组下的模型）时，请求不经过本代理，这里不会出现记录——看板空着先确认一下当前对话用的模型属于 `multi-credits-pool` 分组。

一个账号下常挂着好几段积分，各自的到期时间不同：同一个裂变包可能买了五份，分别在不同的五天到期，另外还叠着体验包、拉新包这类周期不同的额度。账号卡上的分段额度条把这些段并排放，宽度是剩余量、颜色是紧迫度——快到期的段是红的，一段一段看过去就知道哪部分先作废。点开账号看「积分明细」，每一段单独一行，有余额的按到期时间先后排在最上面，用完的沉到底部标「已用完」，用完且已过期的标「已作废」。同名套餐不合并，因为合并之后就分不出哪一份明天到期。同一时刻只展开一个账号。

额度条的颜色只表示这段积分多久之后作废：一周内红、一月内琥珀、更久绿，剩下的段按到期先后从左往右排，和点开后的明细行顺序一致。还剩多少看的是每段的宽度——宽度就是该段剩余量占总剩余的比例，所以额度是集中在一个长周期包里还是碎成一堆短期包，扫一眼就知道。「最早一段 N 天后到期」同样一周内转红、一月内转黄。冷却中的账号会显示「冷却 N 分钟」，那是发起模型请求失败后被暂时跳过的那段时间。

面板跟宿主的主题走：底色、边框、文字灰阶都取自宿主的设计变量，切换深浅色主题不用改任何设置；鼠标悬停时有反馈，展开明细是滑出而不是瞬间跳变，当前正在出账的账号卡带一条绿色描边和一个缓慢呼吸的状态点。

显示名是 `multi-credits-pool`，模型选择器里的分组名、面板标题、侧边栏入口都用这个名字。早期版本的 `plugin.json` 里存过旧显示名，读到时会自动换成现名，不需要手工改。

包名、数据目录、provider id、计划任务名也统一到了这个名字。从改名前的版本升上来时：旧数据目录 `.dsh-workbuddy-multi` 首次启动自动搬到 `.multi-credits-pool`，账号直接还在；模型选择器里残留的旧 provider 分组会被清掉；注册过每日签到的，重跑一次 `credits schedule-install` 会顺带删掉旧名那条计划任务，不会一天签两遍。

添加账号走设备授权：点「添加国内账号」会弹出 WorkBuddy 的授权页，在页面上完成登录即可，面板每 2 秒查一次结果，成功后账号直接出现在看板里。移除会连同本机的令牌一起删掉。

签到状态、剩余积分都来自宿主侧的实时读取；账号卡上的状态胶囊与命令行的 `✔ • - ✘` 对应。

### 调配置

数据目录里的 `plugin.json` 决定端口、显示名与模型清单：

```json
{
  "providerId": "multi-credits-pool",
  "displayName": "multi-credits-pool",
  "port": 34610,
  "defaultContextWindow": 200000,
  "defaultMaxTokens": 64000,
  "autoCheckin": true,
  "minuteOfDay": 600,
  "models": [
    { "id": "glm-5.3", "name": "GLM-5.3", "contextWindow": 1000000, "maxTokens": 64000 }
  ],
  "visibleModels": [],
  "catalogAt": 0,
  "catalogRegion": "cn",
  "secret": "首次启动自动生成"
}
```

`autoCheckin` 与 `minuteOfDay`（自 0 点起的分钟数，`600` 即 10:00）可以在设置卡片里改，改完立刻生效、不用重启。「显示哪些模型」在看板「自动化 → 模型选择」里勾，改完也是立刻生效，存进 `visibleModels`（空数组表示全部显示）。

`models` 是上游清单的缓存，插件自己维护，一般不用手改。要换一套清单（例如改成国际站那一组）就改 `models` 数组并把 `catalogAt` 置 0，`id` 必须是上游认的模型名；国际站账号把 `models` 换成 `default-model`、`fast-model`、`balanced-model`、`primary-model`、`deep-model` 这一组。改 `port`、`providerId` 这些要重启 DSH 生效。

### 轮换规则

按账号顺序挑：没进冷却的优先，同等条件按最近最少使用。额度耗尽冷却 6 小时，登录态失效冷却 30 分钟，限流冷却 5 分钟；请求本身有问题（HTTP 400）不换账号，直接报错。轮换过程对界面不可见，可以用 `credits status` 看各账号剩余积分，判断哪一份额度先用完。

### 一个账号跑到一半没额度了会怎样

分两种情况，取决于代理有没有开始往回吐字：

- **还没开始吐字**：代理在发出响应头之前就发现这个账号额度耗尽（HTTP 402，或正文里的额度耗尽文案），把它记进 6 小时冷却，立刻换下一个账号重发同一条请求。任务不中断，你看到的就是正常回答，只是这次出账的账号换了。
- **已经开始吐字**：这时换账号已经没有意义——半截回答拼另一个账号的回答比报错更糟。代理会把这次中断记成使用流水里的一条失败，把流收尾；宿主看到流没有正常结束，按 provider 的重试策略重发整条请求。重发时那个账号已经在冷却里，自然落到下一个账号。

上游还有第二种拒绝方式：先回 200 开始流式输出，再把额度耗尽放进流里的一片 `error` 事件。这种形状下 HTTP 状态码是 200，看不出问题，代理会读流里的正文，认出额度耗尽就把该账号记进 6 小时冷却。所以不管欠费以 402、429 还是流内错误的形式出现，账号都会被记住，下一次请求绕开它。

所以默认配置下不会「卡死在没额度的账号上」。重试次数在 provider profile 的 `retryPolicy` 里：插件给 `maxRetries` 设了 3、退避从 500ms 起翻倍，并把宿主默认不重试的欠费类错误码（`QUOTA`、`ACCOUNT_QUOTA`）补进可重试列表——不补的话，欠费在宿主眼里是终态，任务会直接停在半路。

**上下文与回答质量不受影响**：账号只决定谁付钱，请求体（`messages`、`tools`、系统提示）原样转发，模型也没变，所以重发之后上下文完整、答案质量一致。唯一的代价是上游提示缓存按账号隔离——换了账号等于换了个租户，这一轮吃不到之前的缓存，首个字慢一点、计费略高。这也是「对话固定」被设为缺省策略的原因：一段对话尽量只用一个账号，缓存才吃得满。

## 常见问题

**提示「另一个签到进程正在处理这个账号」**
同一账号同时被两个进程签到时会出现，被跳过的那个账号本次不签。等对方结束即可；如果确认没有进程在跑（例如上次异常退出），删除数据目录下对应的 `lock-<id>.lock`。

**令牌显示「需重新登录」**
凭据没有 refreshToken，且访问令牌已过期，只能重新 `login` 或 `import` 一份新凭据。

**`schedule-install` 提示创建任务失败**
创建计划任务受机器策略限制。命令会打印完整的 `schtasks` 命令行，可以复制到管理员终端里手工执行；脚本文件已经生成在数据目录，不需要重新生成。

**计划任务到点没有执行**
先看 `checkin-cron.log` 有没有新内容，再运行 `credits schedule-status` 确认任务存在且下次运行时间正确。任务以当前用户身份运行，换用户登录后需要重新注册。

**签到时刻与本地时间对不上**
签到是否有效按 UTC+8 的自然日判定，`credits daemon --at` 也按 UTC+8 解释；`credits schedule-install --at` 交给 Windows 计划任务，按本机时区解释。机器时区不是东八区时，两者需要分别换算。

**余额行显示「读取失败」**
该账号的余额接口调用失败（令牌问题、限流、网络）。签到不受影响，过一会重跑 `credits status` 即可；如果持续失败且令牌状态正常，说明上游接口有调整。

**模型选择器里没有「multi-credits-pool」**
先确认 `%DSH_HOME%\profiles\desktop\package.json` 的 `dsh.profile.bundles` 里有 `multi-credits-pool`，且 `node_modules\multi-credits-pool\index.js` 存在。再确认 `%DSH_HOME%\profiles\desktop\.multi-credits-pool\plugin.json` 是否生成——这个文件由插件第一次启动时写出，没生成说明插件的 `apply` 没跑到，此时看 DSH 日志里 `[multi-credits-pool]` 开头的错误行。代理端口被占用时插件会退回随机端口并改写 provider 配置，不会让宿主起不来。

**选中该 provider 后请求报 401**
代理的 Bearer 与 `plugin.json` 的 `secret` 对不上，常见于换过 secret 或从别处拷了旧配置。重启 DSH，让插件按当前 `plugin.json` 重新登记 provider。

**轮换请求返回 402 或 429**
所有账号要么额度耗尽（402），要么在限流冷却里（429）。等冷却结束，或再用 `credits login` 加一个账号。

**对话报 400，正文含 `11150` 或 `reasoning effort value is not supported`**
当前模型不认这次的推理档位。插件会自动去掉档位重发一次，仍失败才把 400 交给界面；若稳定复现，说明这个模型完全不支持推理档位，换一个模型或在设置里调低推理档位。

**对话报 400，正文含 `11128` 或 `Illegal API invocation from an unapproved channel`**
上游的渠道校验拒掉了这条请求，有四种典型触发：系统提示带了 `developer` 角色（宿主按新协议发出的写法，上游只认 `system`）、系统提示里以 `You are an AI agent powered by DeepSeek Harness.` 开头的文本块、系统提示中段那句 `You are interacting with the user through the DeepSeek Harness Web GUI whose URL the runtime context names.`、以及讲「@ 开头的路径」那一段的开头（`Tokens prefixed with @ are paths the user explicitly referenced.` 往后一百多个字符）。后三者是上游的非官方客户端指纹，按原文逐字比对，少一个标点、换个词就不拦。0.4.1 起代理在转发前把这四处都改掉，系统提示拆成多个内容块时逐块处理；仍然复现说明代理代码还是旧的（它在宿主进程里，刷新页面不会重载），重启一次 DSH 即可。重启后仍复现的话，看 `boot.log` 里那行「上游判请求非法…消息形状」，它写出这次请求的消息角色与内容块类型；同一时刻被拒的那份请求体落在 `.multi-credits-pool\rejected.json`（只有最近一份，排查完可以删掉），把它交给开发者就能直接复现。

**顶栏的「检查更新」一直说没查到远端版本**
查 npm 注册表需要一个能出网的进程，公司网络或代理挡掉 `registry.npmjs.org` 时就会这样。换成镜像源再试：`multi-credits-pool update --check --registry https://registry.npmmirror.com`。这条只影响这一条回执，不影响对话与签到。

**`multi-credits-pool update` 报 `spawnSync pnpm ENOENT` 或装完版本没变**
桌面应用自带的 pnpm 不进 `PATH`，所以命令会自己去找（`MULTI_CREDITS_PNPM` → `PATH` → 数据目录里的 `runtime.json` → 扫安装目录），找不到就退回 `npm install`。0.4.2 起不再直接报 ENOENT。仍失败时：用 `--pnpm "<DSH 安装目录>\resources\runtime\primary-runtime\dependencies\pnpm\bin\pnpm.cjs"` 指给它，或者干脆让桌面应用的插件管理器把这个包重装一次。装完命令会再读一次实际版本，版本没变说明包管理器因为版本约束没动它，用 `--to <版本>` 指定具体版本重试。

**设置页里没有「multi-credits-pool」卡片**
卡片是浏览器半边，需要重启一次 DSH 让客户端 bundle 重新加载。确认 `node_modules\multi-credits-pool\client.js` 存在，且 `package.json` 的 `dsh.client` 与 `exports["./client"]` 都在。

**一次能签几个账号**
没有数量上限，账号之间以 1.2 秒间隔逐个执行。每个账号的设备标识由 uid 派生，在上游看来是各自独立的设备；账号被限制或额度被清空的风险由使用者承担。
