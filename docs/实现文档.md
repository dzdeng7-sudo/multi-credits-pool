# multi-credits-pool 实现文档

## 总体结构

纯 ESM JavaScript，无第三方依赖，无构建步骤。运行环境要求 Node.js 22.19 及以上（`AbortSignal.timeout`、`fetch`、顶层 `await` 均为内置能力）。

```
multi-credits-pool/
├── index.js                 插件入口：导出 name / inject / apply
├── cordis.patch.yml         把插件条目插进宿主组合树
├── bin/credits.js               命令行入口：参数解析、命令分发、退出码
├── src/
│   ├── paths.js             数据目录与文件名
│   ├── store.js             账号库与签到流水的读写
│   ├── protocol.js          上游基址、请求头、UTC+8 时间、响应信封
│   ├── auth.js              设备授权登录、令牌续期、凭据导入
│   ├── checkin.js           单账号签到：加锁、分类结果、落流水
│   ├── balance.js           余额与套餐读取
│   ├── schedule.js          单次扫（sweep）与常驻调度（daemon）
```

数据流向单向。命令行侧：解析参数 → `store` 读账号 → `protocol` 组请求 → `auth` 保证令牌可用 → `checkin`/`balance` 访问上游 → 结果写回 `store` → `summary` 渲染成表格或 Markdown。宿主侧：模型选择器 → 宿主的 `openai-completions` 实现 → 本插件的回环代理 → `rotation` 选账号 → `chat-upstream` 转发 → 上游 SSE 转回 OpenAI 分片。模型清单另有一条旁路：`model-catalog` 每天问一次上游，把结果存进 `plugin.json`，成为模型选择器的可选集合。

## 数据模型

### 账号库

`accounts.json`，结构 `{ "version": 1, "accounts": [...] }`。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 8 位十六进制，见「账号 id」 |
| `label` | string | 显示名，重名时命令行按前缀匹配 |
| `region` | `"cn"` \| `"global"` | 决定所有上游基址 |
| `accessToken` | string | 访问令牌，签到与余额都用它 |
| `refreshToken` | string | 续期令牌；缺省时过期只能重新导入 |
| `expiresAtMs` | number | 访问令牌到期时刻（毫秒）；`0` 表示上游没给 `expiresIn` |
| `refreshExpiresAtMs` | number | 续期令牌到期时刻 |
| `uid` | string | 账号在上游的稳定标识，设备指纹由它派生 |
| `nickname` `domain` `enterpriseId` | string | 登录态带回的资料，用于展示与请求头 |
| `addedAt` `updatedAt` | ISO 字符串 | 写入时间 |
| `lastCheckIn` | object | `{date, status, amount, at}`，最后一次有效签到 |

账号库是明文 JSON，含 access token 与 refresh token，按进程默认权限创建。目录访问权限需要自行控制。

### 签到流水

`checkin-log.jsonl`，一行一个 JSON，追加写入，不重写。

| 字段 | 说明 |
| --- | --- |
| `at` | 写入时刻（ISO 字符串） |
| `kind` | 固定 `"checkin"` |
| `accountId` | 账号 id |
| `date` | 判定日期，`YYYY-MM-DD`，UTC+8 |
| `status` | `claimed` / `already-claimed` / `no-campaign` / `error` |
| `amount` | 领取到的积分数，可能缺省 |
| `message` | 上游原话或本地的错误描述 |

流水是「今天签过没有」的唯一事实来源：`checkedInToday` 只认 `status` 为 `claimed` 或 `already-claimed` 且 `date` 等于今天的行。账号库里的 `lastCheckIn` 只是展示用的缓存，删掉流水不影响签到判定，删掉账号数据库不会丢流水。

读取时坏行直接跳过——一行脏数据不能让整张汇总表失败。

### 使用流水

`usage-log.jsonl`，一行一个 JSON，追加写入。

| 字段 | 说明 |
| --- | --- |
| `at` | 写入时刻（ISO 字符串） |
| `accountId` | 这次请求实际出账的账号 |
| `model` | 请求体里的模型名；解析不出来记 `unknown` |
| `ok` | 是否成功 |
| `conversationId` | 对话键，形如 `prompt_cache_key:<sessionId>`，可能缺省 |
| `kind` | 失败类别，成功时缺省 |
| `promptTokens` `completionTokens` | 上游若在响应里给了用量就记，没给就不写 |

写入点在代理的成功与失败分支（`src/proxy.js` 的 `noteUsage`），整体兜住异常：统计失败只记一条警告，不影响对话本身。成功那条等流跑完才落：响应头先发，用量出现在 SSE 末尾，所以流上挂了一个旁路 `Transform`（`createUsageTap`），一边原样透传一边扫 `data:` 行里的 `usage`，`flush` 或下游断开时把数字交出去。非流式响应另留一段原文按整段 JSON 兜底解析。`aggregateUsage` 按 `USAGE_WINDOW_DAYS`（7 天）切窗口，产出「账号 → 模型」两级计数；`range` 参数另行铺出看板「按时间」用的时间轴（`USAGE_RANGES` 四个档位：昨天、今天按小时切 24 格，近一周切 7 格，近一个月切 30 格，每格带请求数、失败数、输入输出 token 与按模型的分布），今天档只铺到当前小时。流水超过 `USAGE_COMPACT_LINES`（20000 行）时 `compactUsage` 只保留最近的窗口。

采集面只覆盖经过本代理的请求。宿主按会话的 `modelSelection.provider` 选路，对话用的是别的 provider（例如另一个插件注册的 `buddy`、`workbuddy` 分组）时，请求根本到不了 `src/proxy.js`，流水自然为空——看板空着不等于采集坏了，先确认当前会话的模型属于本插件注册的 `multi-credits-pool` 分组。

### 对话固定

`pins.json`，结构 `{ "<对话键>": "<账号 id>" }`。

对话键是 `prompt_cache_key:<sessionId>`，与代理从请求体里取到的键逐字一致。这张表只存用户显式指定的账号，与轮换器内部自动维护的绑定表分开：绑定表随闲置过期、随 `observe()` 清理，固定表不随闲置过期，只在账号被删时解开。界面上的「解除固定」删掉对应键。

### 账号锁

`lock-<id>.lock`，内容为占用锁的进程 id。`checkInAccount` 进入前以 `flag: 'wx'` 原子创建，拿不到就返回「另一个签到进程正在处理这个账号」并跳过该账号；文件已存在时按 `mtime` 判断，超过 10 分钟（`LOCK_STALE_MS`）视为陈旧锁，删除后接管。锁在 `finally` 中释放。

### 插件配置

`plugin.json`，与 `accounts.json` 同目录（数据目录）。首次加载插件时按缺省值生成，之后每次启动原样读回。

| 字段 | 缺省 | 说明 |
| --- | --- | --- |
| `providerId` | `multi-credits-pool` | 注册进 `llm-pi-ai` 的 provider 名，也是模型选择器里的分组标识 |
| `displayName` | `multi-credits-pool` | 模型选择器里显示的名字 |
| `port` | `34610` | 代理监听端口；端口被占用时代理起不来，只记一条错误日志 |
| `secret` | 首次生成 | 代理要求调用方携带的 Bearer，24 字节随机串，落盘复用 |
| `defaultContextWindow` | `200000` | 写进 provider profile 的缺省上下文窗口 |
| `defaultMaxTokens` | `64000` | 写进 provider profile 的缺省输出上限 |
| `models` | 上游清单缓存 | 暴露给模型选择器的清单，元素为 `{id, name, contextWindow, maxTokens}`；启动 15 秒后与之后每 24 小时从上游刷新一次，写回本文件 |
| `visibleModels` | `[]` | 勾掉的模型 id；空数组表示全部可见。看板「自动化 → 模型选择」可改，改完立刻重登记 provider |
| `catalogAt` | `0` | 上次成功刷新模型清单的时刻（毫秒），`0` 表示还没从上游取过 |
| `catalogRegion` | `cn` | 清单取自哪个站，取值 `cn` / `global` |
| `autoCheckin` | `true` | DSH 运行时的每日自动签到总开关，设置卡片可改，改完立刻生效 |
| `minuteOfDay` | `600` | 自动签到的时刻（UTC+8，自 0 点起的分钟数），`600` 即 10:00 |
| `strategy` | `sticky` | 账号调用方式，取值 `sticky` / `sequential` / `expiring` / `round-robin`，看板可切、切完立刻生效 |

`secret` 与账号令牌不同：它只保护「本机哪个进程能调这个代理」，由插件自己生成。设置 `MULTI_CREDITS_POOL_CONFIG` 环境变量可以换一份配置文件，自测脚本用它避免污染真实数据目录。

## 协议层

### 上游基址

| 用途 | CN | 国际 |
| --- | --- | --- |
| 签到 | `https://www.workbuddy.cn/v2/billing/meter/daily-checkin` | `https://www.workbuddy.ai/v2/billing/meter/daily-checkin` |
| 聊天/续期 | `https://copilot.tencent.com` | `https://www.workbuddy.ai` |
| 计费 | `https://www.codebuddy.cn` | `https://www.workbuddy.ai` |
| 登录 | `https://www.codebuddy.cn` | `https://www.workbuddy.ai` |
| 登录请求的 Origin | `https://copilot.tencent.com` | `https://www.workbuddy.ai` |
| 签到 Referer 的站点 | `https://www.workbuddy.cn` | `https://www.workbuddy.ai` |

CN 域名的分工不直观：登录接口在 `www.codebuddy.cn`，登录请求的 `Origin` 必须是 `copilot.tencent.com`，签到的站点是 `www.workbuddy.cn`。三者混用会被上游拒绝。

### 账号 id

```
sha256(`${region}:${uid || accessToken.slice(0, 16)}`).slice(0, 8)
```

同一区域同一 uid 永远得到同一个 id，重复 `login` 因此是覆盖而不是新增；导入没有 uid 的凭据时退化为按令牌前缀区分。

### 设备指纹

```
X-Machine-ID = sha256(`wb2a:machine:${uid}`).slice(0, 36)
X-Session-ID = sha256(`wb2a:session:${uid}`).slice(0, 36)
```

两个头都由 uid 派生，同一账号每次请求稳定，不同账号互不相同。上游把缺失或漂移的指纹当作同一个客户端，所以这里不能随机生成。

### 请求头

四类请求共用 `commonHeaders` 的骨架：`Content-Type`、`Accept`、`X-Requested-With`、`Origin`、`Referer`、`User-Agent`（`CLI/2.63.2 CodeBuddy/2.63.2`）、`X-CodeBuddy-Request: 1`、`Accept-Language`（CN `zh-CN`，国际 `en-US`），再叠加设备指纹。

各自的差异：

- 签到：`Authorization: Bearer`，`Referer` 指向成长中心 `/profile/growth-center`；CN 有 `enterpriseId` 时带 `X-Enterprise-Id` 与 `X-Tenant-Id`，否则带 `X-No-Enterprise-Id: 1`；国际固定 `X-Domain` 与 `X-No-Enterprise-Id: 1`；有 uid 时带 `X-User-Id`。
- 余额：与签到同源站点，但不带成长中心的 `Referer`。
- 续期：`refreshHeaders`，用 refresh token 而非 access token。
- 登录：`loginHeaders`，带 Cookie 不带 `Authorization`。

### 登录（设备授权）

两段式：

1. `GET /v2/plugin/auth/state?platform=CLI`，拿到 `state` 与授权页地址，用系统浏览器打开；
2. 每 2 秒轮询 `GET /v2/plugin/auth/token?state=<state>`，直到拿到 `accessToken`；随后 `GET /v2/plugin/login/account?state=<state>` 补齐 uid、昵称、企业。

未完成时上游返回 HTTP 200 但业务码 `11217`，因此轮询按 `code` 判定而不是 HTTP 状态。轮询间隔 2 秒，整体超时默认 300 秒，可用 `--timeout` 调整。

### 令牌续期

`POST ${CHAT_BASE[region]}/v2/plugin/auth/token/refresh`，返回 `{accessToken, refreshToken, expiresIn, domain}`。

`ensureFresh` 的策略：

- 距到期不足 5 分钟（`REFRESH_MARGIN_MS`）才刷新；
- 同一账号并发调用只发一次请求（进程内 single-flight）；
- 刷新失败但令牌尚未过期，继续用旧令牌，只把失败原因记在返回值里；
- 刷新成功后 `patchAccount` 落盘新的令牌与新的到期时刻。

`expiresAtMs` 落盘是毫秒；上游给的 `expiresIn` 是秒，换算在使用处完成。

### 余额读取

- CN：`/v2/billing/meter/get-user-resource`。
- 国际：先试 `/billing/meter/get-user-resource`，只有 404 或 405（`isPathMiss`）才换带 `/v2` 的路径重试。业务错误原样报出，不做路径回退。
- 企业账号走 `/v2/billing/meter/get-enterprise-user-usage`。

返回体里的额度字段位置不固定，`parsePersonal` 与 `parseEnterprise` 分别按候选键名取值；HTTP 429 表示额度已耗尽。

### 响应信封

`readEnvelope` 统一读文本、尝试 `JSON.parse`、返回 `{status, ok, payload, text}`。上游在限流或网关错误时返回 HTML，因此所有调用方都必须容忍 `payload === undefined`，改用截断后的原始文本作为错误信息。

## 签到流程

```
acquireLock(id)
  → ensureFresh(account)          # 令牌不足 5 分钟就先续期
  → POST CHECKIN_URL[region]      # body 为 {}
  → classify(response, payload)   # 四态判定
  → appendLog({kind:'checkin', ...})
  → patchAccount({lastCheckIn})   # 仅 claimed / already-claimed
releaseLock(id)                   # finally
```

`classify` 的判定顺序：

1. 业务码 `10001` 或消息含「今天已签到 / 已签到 / already」→ `already-claimed`；
2. `data.active === false` 或消息含「活动未开启 / 已过期 / not active」→ `no-campaign`；
3. HTTP 2xx 且业务码为 `0`、`200` 或缺省 → `claimed`，积分取 `data.credit ?? amount ?? points`；
4. 其余 → `error`，`message` 取上游消息，缺省时用 `HTTP <状态>: <正文前 120 字>`。

签到请求不携带日期参数，上游按服务端日期判定，因此漏掉的自然日无法补领。

## 调度

### 单次扫 sweep

`GAP_MS = 1200`：账号之间固定间隔 1.2 秒，避免同一出口 IP 上的并发请求被关联成同一客户端。

默认签到时刻 `DEFAULT_CHECKIN_MINUTE = 600`，即 UTC+8 的 10:00。

`catchUp` 语义：只有当前时间已经过了当天的签到时刻才补签，否则整体跳过并返回 `skipped = 总数`。活动未开门时提前跑只会得到一条失败记录。

`force` 为真时忽略「今天已签」直接重签，否则目标集合由 `pendingAccounts` 给出。

### 常驻调度 daemon

启动后若当天已过签到时刻，先补一次；随后进入循环：`msUntilNextUtc8(minuteOfDay)` 算出到下一个签到点的毫秒数 → `setTimeout` 等待 → 执行 `sweep` → 重新计算。循环不设退出条件，`Ctrl+C` 结束，进程结束即停止签到。

### 计划任务

`installScheduledTask` 在数据目录生成两个文件，再调用 `schtasks`：

| 文件 | 内容 | 编码 |
| --- | --- | --- |
| `run-checkin.cmd` | 计划任务的唯一动作，用 `%~dp0` 定位同目录脚本并转调 | 纯 ASCII |
| `checkin-task.ps1` | 设置 `ELECTRON_RUN_AS_NODE`、`DSH_HOME`、`DSH_PROFILE` 后执行 `checkin --quiet`，输出追加到 `checkin-cron.log` | UTF-8 with BOM |

分两层的原因是两个编码与引号约束同时存在：`schtasks /TR` 的动作串里嵌套引号会被错误拆分，所以动作只留一个不含空格的入口路径；Windows PowerShell 5.1 解析 `.ps1` 时先看 BOM，没有 BOM 会按系统 ANSI 代码页读取，中文路径与中文注释会被拆坏。`.cmd` 保持 ASCII、`.ps1` 带 BOM，两个约束各自满足。

生成的注册命令：

```
schtasks /Create /F /SC DAILY /ST HH:MM /TN "DSH Multi Credits Pool Checkin" /TR "<数据目录>\run-checkin.cmd"
```

`/F` 允许覆盖同名任务，因此重复执行是幂等的。`--dry-run` 只打印两个文件的内容与完整命令行，不落盘也不调用 `schtasks`。

## 宿主插件与模型轮换

### 注册路径

包入口 `index.js` 只做一件事：把 `src/plugin.js` 的 `name`、`inject`、`apply` 三个导出转出去。`cordis.patch.yml` 把一个 id 为 `llm-multi-credits-pool` 的条目插进组合树，条目的 `name` 是本包名，由 profile 的 `node_modules` 解析；`package.json` 的 `dsh.bundle.patch` 指向同一个补丁文件，profile 的 `dsh.profile.bundles` 列到本包时据此读取。

插件不 import 任何宿主包，与宿主之间只有两处契约：

- `ctx.settings` 提供的配置服务，在 `inject = ['settings']` 里声明；
- `llm-pi-ai` 命名空间里 provider profile 的形状：`{displayName, api, baseURL, headers, models, defaultContextWindow, defaultMaxTokens, cacheRetention, compat, retryPolicy}`。

`inject` 必须声明 `settings`：cordis 对服务访问有硬约束，没声明就访问 `ctx.settings` 会抛 `cannot get property "settings" without inject`，插件当场初始化失败。声明之后宿主没提供该服务时插件挂 pending 而不是报错——桌面 App 总是先装好 settings 再加载组合包，这条路径稳定。

登记走 `settings.mutate('llm-pi-ai', [{op: 'set', path: ['providers', providerId], value: profile}])`，卸载时同一路径 `unset`。用 mutate 而不是整段 update，是因为前者只改一个叶子节点，不会覆盖用户在模型页里配置的其它 provider。

### 启动流程

```
apply(ctx)
  → readPluginConfig()                  # 数据目录 plugin.json，缺省写一份并生成 Bearer
  → createChatProxy({port, secret, ...})
  → ctx.effect(...)                     # 卸载时注销 provider、关端口
  → await proxy.ready
  → settings.mutate(set providers[id])  # baseURL = http://127.0.0.1:<实际端口>/v1
  → 15 秒后刷新模型清单，之后每 24 小时一次
```

端口默认固定 34610。provider profile 会把 baseURL 写进宿主配置，端口随进程漂移会让已保存的 baseURL 指向死地址。端口被占用时代理退回系统分配的端口，并按实际端口回写 provider 配置。`apply` 整体包在 try/catch 里，初始化失败只损失一个 provider，宿主的其它能力不受影响。

### 模型清单

模型清单的来源是上游 `GET /console/enterprises/personal/models`（国际站 `/v3/config`），`data.agents` 里 `name === 'cli'` 那一段的 `models` 数组是 CLI 可用的模型 id（有序），`data.models` 给出每个 id 的显示名与上下文/输出上限。`parseModelCatalog` 按 CLI 段的顺序输出，跳过 `disabled === true` 与缺输入或输入上限非正数的条目，其它字段一律不认。

`plugin.json` 的 `models` 就是这份清单的缓存。启动 15 秒后刷新一次，之后每 24 小时一次（`CATALOG_REFRESH_MS`），成功后写回文件并重新登记 provider——宿主的模型选择器不需要重启就能看到新上线的模型。刷新用一个现有账号的身份过网关鉴权，与「谁出账」无关，不占对话额度；没有账号、网络不通、上游返回空清单时直接跳过，缓存保持原样，选择器仍是上次那一份。`CN_MODELS` 只用于首启与刷新失败时的兜底，不保证与上游同步。

登记给宿主的清单会先过一遍 `visibleModels`：用户在看板里勾掉的模型不写进 provider profile，`/v1/models` 也一并回同一份。全部勾掉会让 provider 没有模型可挂，`visibleModelsOf` 因此在这种状态下退回完整清单，Web 接口也会直接拒绝这种勾选。

清单刷新与勾选变更都改同一个进程内状态 `live`：代理的 `modelsOf`、重登记用的 profile、卸载时删的 provider 都从它取。三者各读各的时候，盘上的清单换成新的、选择器里还是旧的。

### 推理等级

宿主只给声明过等级的模型显示「推理等级」下拉，声明写在 provider profile 的每个模型条目里（`reasoningEfforts`）：要么 `false`（这个模型没有推理），要么是一张 `{ 档位: 上游值 }` 字典。字典里没写的档位一律视为不支持，写成空字典会被宿主判成配置非法，所以不支持的模型宁可不写这个字段。

等级来自上游 `data.models[].reasoning`。它有两种形状：

- `{ supportedEfforts: [...], defaultEffort, canDisableThinking }`：列全了可选档位，照抄成字典。
- `{ effort }`：只说明默认按哪一档跑，没给可选集合。这种模型按那一档登记单一项——编一份档位出来只会让用户选到上游不认的值。

档位名直接沿用上游的 `low` / `medium` / `high` / `xhigh` / `max`，请求里的 `reasoning_effort` 就是字典里那个值，与官方 CLI 发的一致。`reasoningEffortsOf` 做这个折算，`parseModelCatalog` 顺手把它带进清单缓存。

老的 `plugin.json` 里存的是没有等级的旧清单，升级后要等下一次刷新（最多一天）才能看到档位。`fillKnownEfforts` 因此在读配置时按 `KNOWN_EFFORTS` 给已知 id 补一份，`CN_MODELS` 与 `GLOBAL_MODELS` 里的兜底条目也直接带上声明。两处对同一个模型的档位必须一致，测试里钉住了这一条。

宿主侧按 `reasoningEfforts` 决定发不发：档位是 `off` 或用户没选等级时不下发 `reasoning_effort`；其它档位原值透传。上游对 `reasoning_effort: 'off'` 也接受，但插件不主动发——`off` 是宿主的「不启用推理」语义，发下去会和宿主认定的「这一轮没开推理」对不上。

### 数据目录与 profile 发现

宿主进程里没有 `DSH_PROFILE`：桌面 App 不会把它放进环境变量。插件因此按下面的优先级定位数据目录（`src/paths.js`）：

1. `DSH_MULTI_CREDITS_POOL_DATA_DIR` 显式覆盖；
2. 扫 `$DSH_HOME/profiles/*`，找 `package.json` 的 `dependencies` 或 `devDependencies` 里声明了本包的 profile；
3. 退回 `$DSH_HOME/profiles/$DSH_PROFILE`（CLI 场景靠这条）。

多个 profile 都声明时，用 `node_modules/multi-credits-pool` 的 realpath 是否等于本包根目录来判定，即以目录联接方式安装的那一份为准；都对不上时取第一个，保证结果不随目录枚举顺序变化。

### 旧版数据迁移

数据目录名、provider id、显示名、计划任务名、环境变量与 Web 前缀都带包名，包改名后这些位置一起换。角色不同，处理方式也不同：

- **数据目录**：`resolveDataDir()` 在目标目录 `.multi-credits-pool` 不存在、而旧目录 `.dsh-workbuddy-multi` 存在时，用 `renameSync` 把它搬过来（同盘，原子操作）。搬不动时（`EPERM`、`EXDEV`，通常是被另一个进程占用）退回逐文件复制，两边都成功才删旧目录，失败只写 `console.error` 与 `boot.log` 留痕，不影响启动。目标目录已存在则两边都不动——宁可让用户手工搬，也不覆盖已有账号库。
- **provider id**：模型选择器按 id 记住用户选过的模型，id 一换等于配置全部作废。`registerProvider()` 因此先读一遍 `providers`，把 `LEGACY_PROVIDER_IDS` 里的条目 `unset` 掉再写新条目，升级后模型页里不会留下一个永远连不上的旧分组。
- **显示名**：见「显示名与配置」一节，读到旧名即换成现名。
- **计划任务名**：旧名注册的任务还在系统里按旧名跑，会和现名那条一天签两遍。`installScheduledTask()` 与 `removeScheduledTask()` 都会顺手删掉 `LEGACY_TASK_NAMES` 里的旧名任务（不存在则忽略），所以重新 `credits schedule-install` 一次就干净了。

### 装载与自检

`boot.log` 记启动痕迹，一行一步，排查「插件没出现」时先看它：

```
module-loaded                              模块被导入（包被宿主解析到）
apply-entered                              宿主调用了 apply
provider-registered <id> via=<mutate|update> base=<url> models=<n>
apply-failed <原因>                         初始化抛错
settings-missing / awaiting-settings        注入的服务没就绪
```

只出现 `module-loaded` 说明插件被挂在 pending，`inject` 声明的服务没有提供；`apply-failed` 带的信息是 cordis 抛出的原文。`trace()` 自身失败不影响插件。

### 请求链路

```
模型选择器（multi-credits-pool · <模型>）
  → 宿主 openai-completions 实现，POST <baseURL>/chat/completions
  → Authorization: Bearer <plugin.json 的 secret>
  → 代理：Host 必须是回环、Bearer 必须相同
  → rotator.order(accounts, { conversationId })   # 未冷却优先；再按所选方式排序
  → ensureFresh(account)               # 距到期不足 5 分钟先续期
  → prepareChatBody：developer → system、自称开头与整句指纹换中性说法、tool_choice 折成字符串、max_completion_tokens → max_tokens
  → chatHeaders 组上游请求，POST /v2/chat/completions（国际站先试 /console/chat/completions）
  → 上游 SSE（本就是 OpenAI 形状）→ 原样透传 → 调用方
```

代理只监听 `127.0.0.1`，`/v1/models` 直接返回 `plugin.json` 里的模型清单，`/v1/chat/completions` 才走上游。账号库为空时返回 401 与「账号库里没有可用账号」。

上游的响应形状与 OpenAI 的 `chat.completion.chunk` 一致：`delta.content`、`delta.reasoning_content`、`delta.tool_calls`、`finish_reason: "tool_calls"`、末尾 `usage` 与 `data: [DONE]`。代理不做任何响应体改写，工具调用与思考增量因此天然可用；成功响应带 `X-Credits-Account` 头，标明这次请求实际由哪个账号出账。

### 请求体整形

上游只认 OpenAI 的旧写法，宿主按新约定发请求体，差一处整条请求就被拒。`prepareChatBody` 在转发前把五处对不上上游的地方统一：

| 宿主发出的 | 上游认的 | 不整形时的表现 |
| --- | --- | --- |
| 系统提示 `role: "developer"` | `role: "system"` | HTTP 400，业务码 `11128`（`Illegal API invocation from an unapproved channel`） |
| 系统或助手消息以 `You are an AI agent powered by DeepSeek Harness.` 开头 | 开头换成 `You are an AI assistant.` | HTTP 400，同样是 `11128` |
| `tool_choice` 对象形态 | 字符串：`auto` / `required` / 函数名 | HTTP 400 |
| 只有 `max_completion_tokens` | `max_tokens` | 按上游默认上限截断，长回答莫名变短 |
| 未声明 `stream` 与 `stream_options.include_usage` | 两者都有 | 上游只按流式返回，末尾没有 `usage` |

`11128` 读作「渠道校验没过」，有四个触发点。一是角色名：宿主把系统提示渲染成 `developer`，这是新协议里的写法，上游只放行 `system`。二是系统提示的首句自称：上游把 `You are an AI agent powered by DeepSeek Harness.` 当成非官方客户端的指纹，system 或 assistant 消息以它开头就整条打回；宿主每轮都带这句，所以只改角色名仍会被拦。三是系统提示中段那句 `You are interacting with the user through the DeepSeek Harness Web GUI whose URL the runtime context names.`：上游按整句逐字比对，含这句就整条回 `11128`，与它出现在哪一块、第几个字符无关。四是讲「@ 开头的路径」那一段的开头：从 `Tokens prefixed with @ are paths the user explicitly referenced.` 起、往后一百多个字符逐字出现就拦，同样与位置无关，只截到这一段前半也照样拦。四处都在转发前改掉，报错文案虽然指向「非法渠道」，实际与鉴权、账号状态无关。

按内容块发过来时，上游逐块校验：自称落在第二个块、前面只隔一个空块或一段中性文字，照样回 `11128`。所以改写逐块做，不是只看第一块。这也解释了一种反复：宿主换了拼装方式之后，同一份提示从「一个字符串」变成「几个内容块」，只看首块的写法就漏过去了。

第三、四处触发点是逐字比对，不是语义规则：少一个句号、把句末标点换成中文、把 `DeepSeek Harness` 换成别的词、把 `Web GUI` 写成 `app`，都能过。这类校验只能按原文定位——把系统提示按前缀切成小段逐段发上游，二分到 5000 字符处的 250 字符窗口，再在其中缩到那两句 221 字符，去掉末尾句号即通过，于是确认为整句指纹。按同一手法定位第四处：逐段发过去只有那一段被打回，段内前缀二分到 110 字符过、117 字符拦，把其中任一个词换个说法即通过。上游随时可能加新指纹，所以定位手法（`rejected.json` 拿真身 → 按段落扫 → 段内前缀二分 → 改词复现）比记住某一句更重要。

带 36 万字符真实上下文、133 条消息、41 个工具的请求体，原样重放是 400，只把首句自称换掉即 200，因此改写固定在这一层。17,105 字符的系统提示里只改那一句、或把 `DeepSeek Harness` 整体换成中性词，同样从 400 变 200。


上游判成非法调用时，代理留一份证据：`boot.log` 记一行消息形状（角色与内容块类型，不含正文），整份请求体写到 `.multi-credits-pool\rejected.json`（只保留最近一份）。形状与正文分开是为了两头都不吃亏——日志轻，可以长期留着；正文重，需要时才知道当时到底发了什么。

其余三条同理：`tool_choice` 折成字符串（`none` 连同 `tools` / `functions` 一起删，等价于关掉工具），别名 `max_completion_tokens` 搬到 `max_tokens`（两者同存时以 `max_tokens` 为准；别名不是正整数就丢掉——`0` 与 `null` 表示「没设」，负数与字符串是坏输入，不洗成合法值），并补上流式字段。

整形范围有意收窄：除消息开头那句自称、中段那句带产品名的 GUI 说明、讲 `@` 路径那一段的首句外，消息正文、工具定义、采样参数、`prompt_cache_key` 与 `prompt_cache_retention` 一律原样带走，`messages` 里其它角色不动，已存在的 `stream_options` 不覆盖。请求体不是 JSON 对象（数组、标量、解析失败）时原样交给上游，由它自己报错——代理不替上游判断请求合法性。同一份请求体整形两次与整形一次结果相同。

### 账号调用方式

`plugin.json` 的 `strategy` 决定健康账号之间的排序，四种取值：

| 取值 | 看板上的名字 | 排序依据 | 取舍 |
| --- | --- | --- | --- |
| `sticky`（缺省） | 对话固定 | 同一段对话固定到首次选中的账号，新对话按 LRU 换下一个 | 上游提示缓存按账号隔离，一段对话只用一个账号才吃得到缓存，速度与命中率最好 |
| `sequential` | 优先用完一个 | 余量不低于 `SEQUENTIAL_FLOOR_CREDITS` 的账号排前，其中最近用得最多的先上；余量见底的按剩得最少垫底 | 换账号次数最少 |
| `expiring` | 优先过期 | 按最早到期时刻升序；同一批到期的先烧余额少的 | 减少积分作废；读不到到期时间的账号排最后，不当作「马上过期」 |
| `round-robin` | 轮询 | 纯 LRU | 消耗摊平，代价是缓存吃不到 |

冷却另算一层：无论哪种方式，冷却中的账号一律按解冻时间排到最后，只有前面的账号都失败才会用到。

对话标识由 `conversationIdOf` 从请求里取。主通道是请求体的 `prompt_cache_key`：provider profile 设了 `cacheRetention: 'long'` 与 `compat.supportsLongCacheRetention`，宿主因此把会话 id 写进这个字段，并附 `prompt_cache_retention: '24h'`。会话亲和头（`x-client-request-id`、`x-session-affinity`、`session_id`、`x-session-id`）在宿主的 `COMPLETIONS_COMPAT_GATE` 里是 `withhold`——写进模型配置会让整个 provider 注册失败，所以不用它；`conversationIdOf` 仍认这四个头，是给直连本代理的其它 OpenAI 客户端留的兼容口。全部标识都缺失时 `sticky` 退化为普通 LRU，不报错。

绑定表只在 `sticky` 下写入，最多保留 500 段对话；一段对话闲置超过 `STICKY_IDLE_MS`（10 分钟）视为新对话、重新选人。切换 `strategy` 走 `/action` 的 `strategy` 动作：写 `plugin.json`、调 `rotator.setStrategy()` 即时生效，不需要重启。

手动固定（pin）是第二张表：对话标题栏右侧的账号按钮把「这段对话用哪个账号」写进 `pins.json`，同时灌进 `rotator.pins`。两张表的语义不同——`bindings` 记「上次碰巧用了谁」，会被闲置超时冲掉；`pins` 记「用户指定了谁」，不随闲置过期，也不会被自动绑定覆盖。`order()` 在 `sticky` 分支里先查 `pins`：被固定的账号若在冷却中则让位给普通排序，否则提到队首。账号被删时 `observe()` 会按当前账号库整表清掉指向它的 pin。

余额与到期时间是排序的输入，由 `/state` 每次取状态时顺带灌进轮换器：`observe(rows)` 更新账号记录，`balanceSink(id, credits, expireAt)` 写 `noteBalance`。看板没被打开过就没有读数，此时 `expiring` 与 `sequential` 按 LRU 兜底。

### 失败分级与冷却

`classifyChatFailure` 把上游响应归成几类，只有换账号有意义的类别才触发轮换：

| 类别 | 判定依据 | 冷却时长 |
| --- | --- | --- |
| `hard_credit` | HTTP 402，或正文含额度耗尽类文案 | 6 小时 |
| `session_dead` | HTTP 401/403，或正文含登录态失效类文案 | 30 分钟 |
| `soft_rate` | HTTP 429，或正文含限流类文案 | 5 分钟 |
| `client` | HTTP 400/422，请求本身有问题 | 不冷却，原样回给调用方 |
| `server` | 5xx、网关返回 HTML、网络错误 | 不冷却，但可换账号重试 |

`client` 这一格里有一类不属于账号问题：`11128` 是请求体与上游的渠道校验对不上（`developer` 角色名、系统提示首句的自称、中段那句带产品名的 GUI 说明、讲 `@` 路径那一段的首句），换账号、加冷却都没用。这类在转发前由「请求体整形」处理掉，真落到这一格时说明上游换了校验规则，该改的是整形逻辑而不是账号状态。

`classifyChatFailure` 只看 HTTP 状态码。上游还有第二种拒绝方式：先回 200 与 `text/event-stream`，再把错误放进流里的一片 `error` 事件——额度在生成过程中用完就是这种形状，此时状态码是 200，状态码这一层看不出任何问题。`classifyStreamFailure` 因此单独判一次流内正文，用的还是同一套 `kind`（`isCreditExhaustion` 判额度耗尽 → `hard_credit`，其余落 `server`），命中后同样走 `noteFailure` 记冷却。这样「这次请求没跑完」与「这个账号不能再用了」两件事都会被记住，用户下一次重发就会落到别的账号上。

轮换器对每个账号最多试一轮：`noteFailure` 记冷却，`noteSuccess` 更新 LRU 时间；全部失败后把最后一次的类别映射成 HTTP 状态返回（402 / 429 / 401 / 502 / 400）。调用方主动断开（`AbortSignal`）不换账号，直接结束。

换账号只在响应头发出之前有效。一旦 `200` 与 `text/event-stream` 已经写出去，代理就不再换人——半截回答拼另一个账号的回答比报错更糟。此时的做法是把这次中断记进使用流水，收掉响应流，让宿主按自己的重试策略重发整条请求。流里的 `error` 事件与连接被掐断都走这条路径，区别只在记下的 `kind`：前者按正文归类（额度耗尽 → `hard_credit`），后者记 `server`。

### 宿主侧重试与欠费兜底

`buildProfile` 给 provider profile 写了 `retryPolicy`：

```js
retryPolicy: {
  mode: 'normal',
  maxRetries: RETRY_LIMIT,              // 3
  retryableCodes: RETRYABLE_CODES,      // 宿主默认五码 + QUOTA + ACCOUNT_QUOTA
}
```

宿主默认只对 `EMPTY_RESPONSE`、`RATE_LIMIT`、`SERVER`、`TIMEOUT`、`TRANSPORT` 重试。欠费在宿主侧被 `classifyPiAiError` 归成 `QUOTA`（上游 402，或正文命中 `isQuotaExceededError` 的几条正则），`ACCOUNT_QUOTA` 是同义的另一路码；这两个不在默认列表里，意味着**宿主把欠费当终态**——如果欠费发生在流已经开始之后，代理没法换号，宿主也不重发，任务就停在半路。补进可重试列表后，宿主会退避重发（500ms 起翻倍），而重发进到代理时那个账号已经因为 `hard_credit` 进了 6 小时冷却，`order()` 自然把请求交给下一个账号。

`maxRetries` 取 3 而不是宿主的默认 5：够走完几个账号，又不至于让一个真的空了的池子卡住十几秒。退避从 500ms 起翻倍，三次合计约 3.5 秒。

上下文不受影响：重发的是宿主手里的同一条请求（`messages`、`tools`、系统提示原样），模型也没变。唯一损失是上游提示缓存按账号隔离，换账号等于换租户，那一轮吃不到之前的缓存，首个字慢一点、计费略高。这也解释了为什么「对话固定」是缺省策略——一段对话只用一个账号，缓存才吃得满。

### 推理档位降级

宿主会把当前的推理档位写进请求体（`reasoning_effort`，有时还有 `reasoning.effort`），而上游各模型接受的档位集合并不一致，不认的时候返回 HTTP 400 与业务码 `11150`（`the reasoning effort value is not supported by the current model`）。这类拒绝与账号无关，换账号也没用。

代理因此做一次同账号的降级重发：先按原样请求；被 `11150` 拒绝时去掉 `reasoning_effort` 再发一次；仍被拒则连 `reasoning` 字段一起去掉。三次都失败才把 400 交给调用方。档位白名单不硬编码——它随上游发版变化，本地列表一定会过期，退一步重发的代价只是一次空请求。

### 进程内自动签到

`apply` 里起一个 60 秒的定时器（`unref`，不阻止进程退出），每次看三件事：`plugin.json` 的 `autoCheckin` 不为 `false`、当前已过 `minuteOfDay`（UTC+8）、账号库里还有今天没签的账号。三者都成立才 `sweep({catchUp: true, quiet: true})`。已有并发保护（`autoRunning`）与销毁保护（`disposed`）。

配置每分钟重读一次，且用的是不落盘的 `peekPluginConfig`——设置卡片改完开关或时刻立刻生效，不会每分钟重写一次 `plugin.json`。

## 浏览器半边与 Web 接口

浏览器半边是 `client.js`，通过本插件的两个 HTTP 路由读写宿主侧状态，不依赖宿主的配置服务：那套服务在版本之间换过名字（`settingsScope` → `configForms`），而插件自己的文件和路由是稳定的事实来源。

同一份面板代码复用在三个落点上，`variant` 只用来看是否铺满中栏：

| 落点 | 插槽 | 注册形态 |
| --- | --- | --- |
| 设置卡片 | `settings.section` → `plugin-settings.item` | 条目 `id` 为包名，`order` 40 |
| 中栏看板 | `main` | `key` 为 `multi-credits-pool-panel`，`inject` 面给出 `variant: 'panel'` 与 `close` |
| 侧边栏入口 | `sidebar.footer.action` | 条目 `id` 为 `multi-credits-pool-sidebar`，`order` 25，`inject` 面给出 `open` |

另有第四个落点只放一个小按钮：对话标题栏右侧的账号选择器注册进 `conversation.session.header.utilities`（`id` 为 `multi-credits-pool-account-picker`，`order` 10）。这个插槽的作用域是会话，宿主会自动把 `sessionId` 传进组件 props，组件据此拼出对话键 `prompt_cache_key:<sessionId>` 去 `pins` 里查当前固定的账号。`main` 与 `sidebar.footer.action` 都要等宿主声明了插槽才注册，因此统一用 `ctx.slots.inject(name, factory)` 包住注册调用；侧边栏还要 `layout` 服务，所以整块放在 `ctx.inject(['layout'], layoutCtx => …)` 里，拿不到 `selectPanel` 就整块跳过。

打开与关闭走宿主的中栏面板选择：`layout.selectPanel('multi-credits-pool-panel')` 开，`layout.selectPanel('conversation')` 收。侧边栏入口据此在「打开」与「收回」之间切换，判断当前是否已打开时依次尝试 `layout.currentPanel()`、`layout.panelInfo`（函数或可读 store 两种形态），都取不到就按「打开」处理——宁可多点一次开，也不让入口点了没反应。`selectPanel` 抛错时回落一次对话面板，避免把界面卡在看板上。

侧边栏那行字显示剩余积分与今日已签数，挂载时读一次 `/state`；读不到就退化成插件名。

改动这三个落点都不影响模型通道：任一注册抛错只写 `console.error`，`apply` 继续往下走。

### 三个路由

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `GET` | `/plugins/multi-credits-pool/state` | 返回动作 key、`plugin.json` 的展示用配置、`collectStatus` 的账号表与合计、`rotation` 预览、`pins` 固定表、`usage` 用量聚合 |
| `POST` | `/plugins/multi-credits-pool/action` | 按 `action` 分发：`checkin` `login-start` `login-poll` `rename` `remove` `config` `strategy` `pin` `unpin` |
| `GET` | `/plugins/multi-credits-pool/update-check` | 回 `{ current, latest, updateAvailable, command, checkedAt }`，`?force=1` 跳过缓存 |

状态文档按 15 秒缓存：面板挂载时只看一次网络，刷新按钮与改配置会主动失效缓存。账号表里不含任何令牌，只有 `has*` 之外的展示字段。

### 检查更新

面板没法自己换掉运行中的代码——装在那个位置的文件被宿主进程拿着——所以「更新」拆成两半：面板负责说清有没有新版，真正的安装交给命令行。

`src/update-check.js` 查 npm 注册表：`GET <registry>/multi-credits-pool/latest`，只取回执里的 `version`，与 `localVersion()`（读包内 `package.json`）过 `compareVersions` 比一次。回执按 `ttlMs`（缺省 10 分钟）缓存，并发的多次调用合并成一次请求；网络失败、404、回执里没有 `version` 一律回 `undefined`，界面据此显示「没查到远端版本」而不是报错——查不到新版本不该让面板变红。

`command` 字段直接给出该执行的命令（`multi-credits-pool update --to <版本>`），面板原样显示成可复制的代码块，用户不用去翻文档拼版本号。

命令行侧是 `bin/credits.js update`：

| 参数 | 作用 |
| --- | --- |
| 无 | 装最新版：`pnpm add multi-credits-pool@<latest> --dir <profile>` |
| `--check` | 只查不装，打印当前版本与远端版本 |
| `--to <版本>` | 装指定版本，可用来回退 |
| `--registry <URL>` | 换注册表（镜像、内网源） |
| `--dry-run` | 打印将执行的命令，不真装 |

安装走 profile 目录下的 `pnpm add`，与宿主装插件用的是同一套依赖树，装完重启 DSH 生效。装完再读一次 `localVersion()` 复核——`pnpm` 可能因为版本约束把包留在原地，这时要如实报告失败，而不是打印一句「已更新」。

### 守卫

两道，各挡不同的东西：

| 守卫 | 挡什么 | 实现 |
| --- | --- | --- |
| 回环 `Host`（`POST` 另查 `Origin`） | DNS 重绑定页面——请求会带着攻击者域名到达 | 解析 `Host`/`Origin` 的主机名，只接受 `127.0.0.1` / `localhost` / `::1` |
| 动作 key | 本机其它进程——回环地址不是身份，任何本地程序都能伪造 `Host` | 进程启动时 `randomBytes(24)`，`GET state` 下发给同源卡片，`POST` 用 `X-Credits-Key` 带回来，`timingSafeEqual` 比较 |

`login-start` 与 `login-poll` 之间用内存表按 `state` 记住这次登录尝试（含 cookie jar），5 分钟没完成就作废；登录成功立刻写进账号库并让状态缓存失效。

### 面板内容

看板分四个页签：账号池、使用看板、签到动态、自动化。

顶栏左侧是项目名与一行摘要（账号数、剩余积分、今日签到进度），右侧依次是 `Star` 星标、检查更新、刷新、签到（宽屏再跟一个关闭）。星标是通向仓库的外链胶囊：地址取自 `client.js` 的 `REPO_URL` 常量，`target="_blank"` 配 `rel="noopener noreferrer"`，图标是一条 24×24 的五角星路径，悬停时上浮并让星形旋转 72°。它排在刷新与签到之前，用品牌色描边而不是按钮底色，读起来是「去仓库」而不是又一个操作。

检查更新是一个按钮两种态：平时写「检查更新」，查到新版本就直接写成「可升级 vX」并转成警示色，同时标签栏下方横一条提示，写着当前版本、最新版本与那条安装命令。查到之前不占地方——没更新的插件不该在顶栏常驻一条公告。点它走 `/update-check?force=1`，结果回来后按钮与提示条一起换。

账号池按「指标块 → 账号调用方式 → 账号卡」三段排：

- 指标块：今日获得、本月累计、剩余积分、今日已签（`checkedIn/accounts`，全签完转绿）。
- 账号调用方式：四个分段按钮（对话固定 / 优先用完一个 / 优先过期 / 轮询），当前模式高亮，下面一行写这个模式的代价；右侧在 `sticky` 下显示已固定多少段对话。每个按钮悬停或获得焦点时浮出该模式的完整说明，未选中项也有解释——只解释当前项时，用户无法在按下之前比较四种模式。点一下走 `strategy` 动作，写配置并热切换。
- 账号卡：收起态是一行摘要加一条分段额度条，点整卡展开逐段明细。
  - 摘要行：首字母头像、账号名、今日状态胶囊（已签到 / 今天已签过 / 活动未开启 / 未签到 / 失败）、今日所得、冷却剩余；第二行是区域、`uid …末四位`、企业标记与「N 段积分（M 段有用量）」；右侧是大号剩余积分与总量；最右是展开箭头。
  - 分段额度条：每段积分按剩余量占总剩余的比例分宽度，颜色取该段到期日的紧迫度，剩余为 0 的段压到 35% 不透明度。一条总进度条回答不了「哪一段先作废」，拆段之后额度是集中在长周期包里还是碎在一堆短期包里直接看得出来。
  - 底部一行：最早一段还有多久到期（一周内红、一月内黄）与令牌到期天数。
  - 展开区（`积分明细`）：逐段表格，每段一行——套餐名、剩余 / 总量（附迷你条）、到期时间、距作废还有多久。有余额的段按到期时间升序排在最前，用完的段沉底并标「已用完」，用完且已过期的标「已作废」。同名套餐不合并：合并后就看不出「同一个裂变包 5 份、各差一天到期」这件事。点开时同一时刻只展开一个账号，展开态存在面板的 `state` 里，所以刷新不会把它弹回去。「签到」「改名」「移除」三个按钮在展开区里。点「改名」不弹窗，就地换成输入框加「保存」「取消」：Enter 保存、Esc 取消，名字为空时保存按钮不可点，输入框在出现时预填当前账号名。桌面端窗口不实现 `window.prompt`，弹窗式改名在那里点了等于没反应，所以改成组件内的就地编辑；草稿存在面板状态里，输入期间后台刷新列表不会把已敲的字冲掉。

使用看板读 `/state` 的 `usage` 段，按「指标块 → 按账号 → 按时间」排：

- 指标块：请求总数、失败请求、输入 token、输出 token，都按最近 `USAGE_WINDOW_DAYS` 天统计。
- 按账号：每个出过请求的账号一行，显示请求次数与失败数，下面一条按模型切分的横条（宽度取该模型请求数占该账号总请求数的比例），再列出模型与次数。看板回答的是「哪个账号在跑哪个模型」，所以账号是主轴、模型是分段；颜色只用来区分模型，不表达好坏。
- 按时间：一张环形饼图，每个有请求的时间段占一段扇区，扇区角度正比于该段请求数占窗口总数的比例——一整圈就是窗口内的全部请求。卡片头右侧四档切换——昨天、今天、近一周、近一个月，默认近一周。昨天与今天按小时切格（今天只铺到当前小时，后面的小时还不存在），近一周与近一个月按天切格（分别 7 格与 30 格）。档位跟着 `GET /state?range=` 走：时间轴由服务端按档位铺格，前端只画收到的格子，换档就重新拉一次 `/state`。
  - 扇区用两条同心圆弧加两条沿半径的直边拼成（`donutSlicePath`，半径 78 与 52，画布 168×168）。段与段之间留一道按角度算的缝：份额最大的段吃满 `DONUT_GAP_DEG`，其余按自己占最大段的几分之几收窄，扇区多到 16 段以上时缝再压到 45%，免得缝把只占很小一角的段吃光。角度不足 1.2° 的段画不出弧，退化成一条从内圈到外圈的细线。
  - 没有请求的时间段不占角度：它们不贡献任何面积，硬留一格只会在环上凭空多出一段与数量无关的弧。这些段的交代方式是圆心下方那句「N 个时间段没有请求，不占环上的角度」，以及整环底层那圈浅色虚线——它标出整段时间的范围，让读者知道环是完整的。
  - 扇区颜色只看这一段稳不稳：全成功用品牌色，有失败但没过半用琥珀，失败过半用红色。
  - 圆心写窗口内请求总数、单位与当前档位名，回答「一整圈等于多少」。
  - 环右侧是按请求数从多到少的图例（最多 6 条），每条给色块、时间桶与占比；图例与扇区一样可点。
  - 失败按「账号尝试」计数：一次对话换了号重试，两个账号各记一条失败，所以悬停文案后面注明「换号重试记在各自账号上」。
  - 悬停给出这一段的完整读数（时间桶、次数、失败数、输入输出 token），点一下把这一段固定在卡片下方展开按模型的分布，再点一次收起。换档会清掉已固定的段，以免新旧时间轴的 key 对不上。
  - 卡片头的汇总行写窗口内总数、失败数与最忙的那一段。
  - 换档在面板顶层发生：档位状态放在取数之前，`usePanelState({ range })` 拿它去拼 `?range=`，所以点哪一档就按哪一档重新拉 `/state`，印章、圆心、时间格与图例一起换。连续换档时 `usePanelState` 用请求序号作废过期回包——先发的慢响应回来时序号已经对不上，直接丢弃，界面停在最后点的那一档。
- 没有任何流水时给一句引导，而不是空白卡片。

签到动态页读 `recent`：最多 8 条签到流水，带相对时间、账号名、结果与所得。

自动化页是控制行：每日自动签到开关、签到时刻（`<input type="time">`，按 UTC+8 解释）、添加国内/国际账号，下面一张「模型选择」卡片。

模型选择卡片按 `/state` 的 `config.catalog` 铺出勾选框，勾上的模型才写进宿主 provider 的 `models`；卡片头部显示 `config.lastRefresh`（清单上次从上游取回的时刻），旁边的「立即更新」直接触发一次刷新。勾选提交到 `visible-models` 动作，服务端存下被勾掉的 id 并重登记 provider，宿主的模型选择器当场跟着变；一个都不勾会被前端与接口各拦一次——空清单会让宿主的模型选择器整条消失。

添加账号走设备授权：点按钮后弹浏览器授权页，面板每 2 秒轮询一次，完成后自动刷新账号表。等待期间控制行上方出现一条带授权链接的提示条，可以取消。

`/state` 里每个账号行除了展示字段，还带这些与分段积分有关的字段：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `packages` | 余额接口的 `Accounts` 逐条 | 每一段积分：`name`、`code`、`remain`、`size`、`used`、`startTime`、`endTime`、`endTimeMs`、`unlimited` |
| `groups` | 同上按套餐名聚合 | 概览用：同名的多期合成一条，`endTime` 取组内最早的一期 |
| `creditsTotal` | 各段 `size` 之和，并被 `TotalDosage` 托底 | 剩余占比的分母 |
| `creditsExpireAtMs` | 还有余额的段里最早的 `endTimeMs` | 账号摘要上的「最早一段 N 天后到期」 |
| `unlimited` | 企业版 `limitNum === -1` | 不限量账号不能把 `-1` 当数字画 |

每个套餐的到期时刻取 `CycleEndTime`（这一段积分本周期的结束），`ExpiredTime` 兜底；`DeductionEndTime` 是产品级长期扣减截止（实测是 2035 年那种日期），拿它当到期只会把「马上作废的积分」显示成「还能用十年」，所以不参与。上游同时给字符串与毫秒两种形态：字符串原样显示（那是上游时区的墙上时间），毫秒给排序与倒计时——让浏览器自己解析字符串会按本地时区偏几个小时。

此外每行还带 `uidSuffix`、`expiresAtMs`、`cooldownUntil`（来自 `AccountRotator.snapshot()`，仅在冷却未到期时出现）。冷却信息让看板能显示「冷却 N 分钟」，与轮换判定同源。

`/state` 另有两段给「对话固定」用：`pins` 是对话键到账号 id 的映射，`rotation.preview` 是按当前方式排好的账号 id 序列（`preview[0]` 就是下一个会出账的账号）。对话标题栏的选择器两者都用：`pins[对话键]` 有值就显示那个账号并标成已固定，没有就显示 `跟随：<preview[0] 的账号名>`。

选择器的交互按「先看后用」排：

- 收起态是一个小按钮，文字是 `跟随：账号名` 或 `账号名`，悬停给出这句话的完整解释（下一个请求会走谁、点开能做什么）。
- 展开后是账号清单，当前固定的账号打勾，每项悬停给出该账号的剩余积分与冷却状态——选哪个账号这件事，余额和可用性是决定因素，不该逼用户切到看板去查。
- 已固定时底部多一项「解除固定」，回到按当前调用方式自动分配。
- 非 `sticky` 模式下清单项全部禁用，并说明「固定账号要先切回对话固定」：别的模式排序不看固定表，给出能点却无效的选项比禁用更糟。

固定动作走 `/action` 的 `pin`（`{conversationId, id}`）与 `unpin`（`{conversationId}`），回执里带回整张 `pins`，界面据此立刻重画，不必等下一次 `state` 刷新。

设置卡片注册进宿主设置页的共享容器：`settings.section` 里 id 为 `plugin-settings` 的条目（子插槽 `plugin-settings.item`），本插件往里加一条 id 为包名的条目。同 id 容器已存在时只注册自己的条目——多个插件共用一个「插件设置」区块，容器只能有一个声明者。

显示名由 `plugin.json` 的 `displayName` 决定，缺省 `multi-credits-pool`；`readPluginConfig` 与 `peekPluginConfig` 都会把旧版本存下的旧显示名换成缺省名，因此升级后不需要手工改配置。

### 样式层

面板样式是一张随插件下发的样式表（`client.js` 里的 `PANEL_CSS`），挂载时由 `ensureStyles()` 写进 `document.head`：

| 环节 | 做法 |
| --- | --- |
| 注入 | 建 `<style>` 节点并打上 `data-plugin` 与 `data-plugin-css` 两个属性，热重载时按 `data-plugin-css` 找到旧节点改 `textContent`，不会堆出多张同名表 |
| 取色 | 全部取宿主的 `--dsw-alias-*` 变量（`bg-layer-1/2/3`、`border-l2`、`label-primary/secondary/tertiary/dimmed`、`state-success/warning/error-primary`、`brand-primary`），各自带一个缺省值，宿主换主题跟着变 |
| 半透明 | 用 `color-mix(in oklab, var(--credits-fg) 8%, transparent)` 这类混色，深浅两套主题都成立；写死颜色的只有三种语义色与一个卡片阴影 |
| 动效 | 悬停、展开、淡入、骨架微光、当前出账账号的呼吸点都是样式表里的 `transition` 与 `@keyframes`（`credits-in`、`credits-rise`、`credits-shimmer`、`credits-pulse`） |
| 无障碍 | `prefers-reduced-motion: reduce` 下把所有动画与过渡压到 0.001s |
| 兜底 | 注入失败只写 `console.error`，组件仍按默认样式渲染，不影响功能 |

中栏在宿主里是 `overflow:hidden` 的弹性列（`centerCol`），面板挂上去就是它的直接子元素，宿主不替面板滚动。所以滚动、限宽与吸顶三层都由面板自己给：

| 层 | 元素 | 职责 |
| --- | --- | --- |
| 滚动层 | `.credits-page` | `flex:1 1 auto` + `min-height:0` + `max-height:100%` + `overflow-y:auto`，内容比窗口高时在面板内部滚，不会在底部被裁掉；`scrollbar-gutter:stable` 让出现滚动条时卡片不横向跳动 |
| 内容层 | `.credits-body` | `max-width:920px` + `margin-inline:auto`，宽窗口下卡片不铺到整屏 |
| 吸顶层 | `.credits-sticky` | 顶栏与页签 `position:sticky`，滚动时功能按钮始终可点，底色取 `--dsw-alias-bg-base` 盖住下方内容 |

设置卡片是另一种容器（设置页里的一段，不是中栏），`[data-variant="settings"]` 把这三层退掉：不吸顶、不独立滚动、不留内边距，跟随设置页整体滚动。

颜色只承担一种语义：**多久之后作废**。额度条与明细里的圆点共用同一套取色（`EXPIRY_COLORS`：一周内红、一月内琥珀、更久绿、未知灰），所以条子的分段顺序和明细行的顺序一致，从上到下、从左到右都是「先作废的在前」。额度条每段的宽度按该段剩余量占总剩余的比例分配（`flex-grow`），剩余为 0 的段压到 35% 不透明度。

## 发布流程

发布脚本 `tools\publish.ps1` 按白名单把可公开的路径拷进 `.publish`，在暂存目录里建仓、提交并推送。`tools/`、测试数据目录和截图产物都不在发布清单里，只留在本机。脚本先做文件泄漏检查，任何一处命中本机路径或用户名都直接中止；远端已有提交时，新的提交挂在远端最新提交之后，推送因此是快进。各轮自测项与结果见 TESTING.md。

## 汇总与渲染

`collectStatus(accounts, {withBalance})` 逐账号取数：签到状态来自流水，余额来自 `fetchCredits`。单个账号的余额请求失败只把该行标成「读取失败（原因）」，不影响其余行，也不影响退出码。

`renderTable` 是终端表格：按显示宽度对齐（`displayWidth` 把全角字符算 2 列），长文本用 `oneLine` 压成单行并截断。

`renderMarkdown` 输出四段：今日概况、账号明细、套餐明细、本月累计。表格单元格经过 `markdownCell` 处理，把 `|`、换行、空白压平，避免 HTML 错误体把表格撑破。

## 错误处理与编码

- **BOM**：`stripBom` 在每次读文本时剥掉 U+FEFF。Windows 上导出的凭据文件常带 BOM，不剥会让 `JSON.parse` 直接失败。
- **坏行**：流水读取逐行 `try/catch`，坏行跳过。
- **禁止管道**：`scheduler-task.js` 调用 `schtasks` 时用 `stdio: 'ignore'` 收尾。在受限环境里给子进程接管道会得到 `EPERM`，而这里本来也不需要它的输出。
- **凭据不外泄**：`list --json` 输出账号元数据，`accessToken` 与 `refreshToken` 只报告「有/无」，不回显内容。
- **退出码**：`0` 成功；`1` 有账号签到失败或命令出错；`2` 未知命令。

`tools/render-harness.mjs` 是预览与界面断言共用的渲染夹具：内置一个够用的迷你 react（`useState`/`useEffect`/`useCallback`/`useMemo`/`useRef`）、HTML 序列化与 `setInterval`/`setTimeout`/`fetch` 的桩，把 `client.js` 用 `new Function` 跑起来，从 `__ModuleLoader__` 抓 `main`、`sidebar.footer.action` 与 `conversation.session.header.utilities` 三个组件。它导出 `createHarness()` 与一份三账号的样例状态（一个有五段不同到期日的积分、一个企业账号、一个令牌过期且冷却中的账号，另带一份用量聚合与一条固定记录），`ui-test.mjs` 与 `preview.mjs` 都从它取数。

每次 `renderScreen` 前会清空状态表：不清的话，连续渲染会继承上一次的 `useState`（页签停在上一个、菜单停在展开态），断言就会对着错的画面下结论。

`tools/preview.mjs` 只做版面：生成 `preview.html`（900 宽）、`preview-narrow.html`（620）、`preview-expanded.html`（强制展开逐段明细）、`preview-usage.html`（使用看板）、`preview-update.html`（查到新版本时的顶栏与提示条）、`preview-picker.html`（对话头部选择器的展开菜单）、`preview-settings.html`（520，设置卡片宽度）、`preview-sidebar.html`、`preview-diag.html`。这些页面的外层照抄宿主的 `centerCol`（`display:flex` + `overflow:hidden` + 固定高度），面板因此和在中栏里一样只有窗口那么高。带 `--shot` 时用无头 Chrome 依次拍成 PNG，带 `--probe` 时把面板的 `clientHeight`/`scrollHeight`/`overflowY` 写进 `document.title` 再读回来——「内容被裁掉」和「内容能滚动」在截图上看不出分别，只能量数值。
